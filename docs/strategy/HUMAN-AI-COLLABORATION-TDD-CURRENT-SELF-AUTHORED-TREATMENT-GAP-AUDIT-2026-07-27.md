# Current Self-Authored TDD Treatment Gap Audit

Date: 2026-07-27
Status: repository-evidence audit; no model or candidate execution

## Outcome

The current TDD comparison has no identity-bound self-authored TDD-method
treatment symmetric with the source-pinned Matt and Superpowers candidates.
The self-authored inventory currently exposed by the comparative protocol is
the three-Skill orchestration chain:

- `intent-contract` for intake sufficiency;
- `capability-router` for route selection and reroute; and
- `closure-contract` for evidence-backed closeout.

Those are upstream and downstream phase controls. The comparative protocol
explicitly says they are not implementation methods, are not primary acceptance
arms, and cannot be credited for TDD implementation quality as one combined
treatment.

This is a current experiment-treatment identity and attribution gap. It is not
evidence that another self-authored Skill is necessary.

## Four distinct layers

### Hard standards

The current TDD protocol keeps the following requirements identical across
primary arms: visible and hidden oracle success, an ordered valid RED before
production mutation, mutation-sensitive tests, public behavior and independent
literal expectations, exact write scope, and no unauthorized dependency,
network, Git, configuration, Plugin, MCP, or external write.

These are mandatory common controls. They are not a Skill treatment and cannot
be credited to Matt, Superpowers, the approved adapted payload, or a future
self-authored candidate.

### Upstream orchestration

The three self-authored Skills are identity-bound in the older comparative
protocol, but each is classified `eligible-only-as-phase-control`.
`SE-SELF-CHAIN-PHASED` is not a primary acceptance arm and does not require
RED/GREEN as its own method claim.

Combining intake, routing, and closeout into one exposure would also create a
multi-Skill and multi-phase confound rather than a treatment symmetric with one
Matt TDD tree or one Superpowers TDD tree.

### TDD treatments

The current new-feature TDD protocol selects only:

- `matt.current-tdd`; and
- `superpowers.6.2.0-test-driven-development`.

Its native arm deliberately has no treatment. There is no self-authored
`selectedTreatment`, no self-authored TDD arm, and no self-authored
candidate-specific admission.

The repository does contain `skill.curated.tdd`, an approved six-file adapted
payload with a release-manifest identity. That does not change this conclusion:

- its registry source is `github:mattpocock/skills`;
- its admission marks it `thirdParty=true`;
- it is byte-distinct from the current three-file Matt projection;
- it is not a member of the self-authored orchestration chain; and
- it has no selected arm in the current TDD protocol.

It is therefore an identity-bound approved adapted third-party payload, not a
current symmetric self-authored treatment. A future protocol could evaluate it
as its own governed candidate, but this audit does not add such an arm or
authorize execution.

Current Matt and Superpowers 6.2.0 each have a diagnostic-only identity-bound
repository admission, but both dispatches remain blocked. Neither admission
establishes candidate delivery, causation, value, or a valid formal comparison,
and neither creates an approved release entry or live execution authority.

### Runner and ledger

The append-only identity-ledger and runner-preflight PoCs are infrastructure
for admission, reservation, identity, construction, and cleanup boundaries.
They do not supply a TDD method.

Their own evidence says the runner remains injected-factory-only, formal-runner
integration is absent, live ledger authority is not configured, current
candidate dispatch is unauthorized, and candidate invocation or body delivery
is unproved. Infrastructure readiness must not be counted as a treatment arm.

## Why the gap does not justify self-authoring

The current comparison is already blocked by zero valid native baseline,
unproved candidate-specific treatment delivery, dispatch-time freshness, and
runner or ledger integration. Those are measurement and execution-boundary
problems. Adding a new candidate would not resolve them.

Native TDD behavior, current Matt, Superpowers, and the approved adapted TDD
payload also have not been shown to leave a repeatable functional or
collaboration shortfall that requires a new method. Candidate absence alone is
not residual-gap proof.

Before any self-authoring decision, evidence would need to:

1. resolve current comparison validity and attribution blockers;
2. evaluate existing native, external, or approved-adapted capabilities on one
   named shortfall;
3. demonstrate a repeatable residual TDD-method gap;
4. define a distinct single-method identity, provenance, overlap boundary,
   protocol arm, admission, and attribution oracle; and
5. obtain separate authoring and portfolio-mutation authority.

## Claim and execution boundary

This audit read repository evidence only. It made zero model requests, zero
candidate dispatches, and zero Skill invocations. It did not install anything,
change CC Switch or global configuration, use external access, mutate the
program map, or change the global verifier.

It does not prove behavior or value for the self-authored chain, Matt,
Superpowers, or `skill.curated.tdd`; candidate delivery or causation; formal
comparison validity; a self-authored residual gap; implementation necessity;
preference, superiority, production readiness, or cross-host value.
