# YIYUAN Accord v3.0.1

YIYUAN Accord v3.0.1 is the first full release of the adaptive product shape:
a small portable reliability kernel plus context-tailored, mechanism-neutral
outcome delivery. The major version records an incompatible product-boundary
correction; it is not a claim of universal correctness or production safety.

## What changed

- Goal, requirement, capability, authority, evidence and cost now drive a live
  route through context, state, effect, resource, continuity, topology and
  lifecycle.
- Process-loss control preserves one reviewable chain from the latest demand
  and corrections through goal, authority, route, implementation, evidence,
  acceptance and release claim; material drift replays only affected
  downstream work.
- Codex and Claude expose the same `deliver-demand-driven-outcome` Skill name
  and the host-qualified human names `YIYUAN Accord for Codex` and
  `YIYUAN Accord for Claude`.
- The progressively disclosed Skill discovers current capabilities, can use
  reliable official or external sources when native and marketplace surfaces
  are insufficient, owns supported configuration and topology mechanics,
  recomputes on drift, and prefers native hot reload or atomic update with
  health check and rollback.
- Installation remains latent availability, not unconditional per-message
  activation. A healthy sufficient native route is a correct no-op.
- Skill, plugin, App, MCP, Hook, configuration, state, runtime, cloud carrier or
  another mechanism is neither mandatory nor permanently forbidden; every
  mechanism remains scoped, observable, reversible and retireable.
- Resource stewardship observes capacity and exposure, attributes identity,
  ownership, lease and state, admits minimum sufficient concurrency, rebalances
  or degrades under pressure, releases only attributable task-owned resources
  and verifies post-state. Native whole-loop governance is a no-op; performance
  tracing is diagnostic evidence, not an optimizer or release receipt.
- Schema v3 authority, the derived dynamic-relation model, fail-closed verifier,
  GT-07 fresh-carrier continuity, GT-11 adaptive repair, GT-12 bounded
  resource-stewardship evaluation and complexity/process-loss controls replace
  the retired preview.2 release premise without moving historical tags.

## Install

Codex:

```powershell
codex plugin marketplace add yiheng8023/YIYUAN-Accord --ref v3.0.1
codex plugin add yiyuan-accord-codex@yiyuan-accord
```

Claude Code:

```powershell
claude plugin marketplace add yiheng8023/YIYUAN-Accord@v3.0.1
claude plugin install yiyuan-accord-claude@yiyuan-accord
```

For Claude Desktop Chat, Claude web chat or Cowork, add the Accord GitHub
repository under **Customize > Plugins**, install **YIYUAN Accord for Claude**,
start a new chat and confirm `deliver-demand-driven-outcome` is visible.

Start a new task or session after installation. Installation and enablement do
not prove activation or behavior; explicit Skill selection is only needed for
a deterministic exposure check.

## Evidence boundary

The representative behavior claim requires exact Codex-local GT-07 continuity,
GT-11 repair and GT-12 resource-stewardship observations bound to the same v3
Skill. GT-07 covers only its disposable fresh-carrier chain with capacity
recorded as unknown, independent destination verification before fixture-source
release and exact cleanup. GT-11 additionally binds the latest demand and
compatible correction through goal, authority, route, implementation,
evidence, acceptance and final claim. GT-12 covers only its supplied capacity
and ownership fixture; neither task establishes universal context management,
automatic system optimization or reclaim. Claude Code autonomous closeout and
current Claude client behavior remain unclaimed; static package validation is
not promoted into behavior equivalence.

The first Windows atomic-update fixture failed because its implementation
called `fsync` on a read-only descriptor and left one transaction file. That
failure remains recorded as `FC-V3-01`; replay from the fixture implementation
boundary passed health failure, byte-exact rollback and cleanup. This is not
evidence of live host-plugin hot update.

The first pushed v3 candidate, `06feba0238b962f2cf74e6e0dea4737e67151010`,
then exposed `FC-V3-02`: its seven-digit fractional evidence timestamp was
accepted by newer interpreters but rejected by Python 3.10 on Ubuntu, Windows
and macOS. The earliest affected boundary was the timestamp parser, which now
normalizes sub-microsecond precision before standard-library parsing. The
current interpreter matrix is compatibility evidence rather than a permanent
product whitelist; the failed SHA is not release-eligible.

The current GT-07 replay exposed `FC-V3-03`: two fresh ephemeral Codex carriers
read and applied byte-identical transient 3.0.1 Skill content, completed the
verified handoff and cleaned the fixture, but a later marketplace refresh
restored the locally configured immutable `v2.0.1-preview.1` ref and removed the
unpublished 3.0.1 cache. This is correct configured-version reconciliation, not
durable candidate hot-update proof. The earliest affected boundary is installed
version authority: after the public tag exists, release verification must move
the bounded local marketplace to exact `v3.0.1`, verify installed bytes and
fresh-carrier activation, and roll back on failure. Moving `main` is not the
user installation route, and current-session in-place reload remains unproved.

The full-release candidate requires an unchanged clean SHA to pass canonical
and independent local review, the three required Ubuntu/Windows/macOS GitHub
Actions checks, a condition-fit Codex Cloud result or bounded limitation, and a
separate named-human decision before tagging.
After tagging, the bounded installed-update replay remains part of public
release verification and cleanup.

## Release integrity

The release uses one lightweight `v3.0.1` tag, a non-prerelease GitHub Release
and no attached assets. Existing `v2.0` and `v2.0.1-preview.1` tags remain
immutable; `v2.0.1-preview.2` remains an unreleased historical checkpoint.
