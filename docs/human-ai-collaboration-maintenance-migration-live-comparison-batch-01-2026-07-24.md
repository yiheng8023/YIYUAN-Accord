# Human-AI Collaboration Maintenance/Migration Live Comparison — Batch 01

Date: 2026-07-24
Status: three valid Spark/low pairs complete; bounded native association,
without Skill causation, general preference, or portfolio action

## Outcome

Three valid paired runs compared:

- `SE-MAINT-NATIVE-SPARK`: all configurable user Skills disabled;
- `SE-MAINT-CC-DEPRECATION-MIGRATION`: only the exact CC
  `deprecation-and-migration` candidate selected.

All six runs used Codex Desktop app-server `0.145.0`,
`gpt-5.3-codex-spark/low`, the same v3 private oracle, no network, approval
`never`, disposable roots, and the same mutable-file boundary.

Both arms passed visible tests in all three repetitions. The full hidden
contract passed:

| Pair | Native | CC candidate |
| --- | --- | --- |
| `r1` | pass | fail — `migrationStatus` remained `not-evaluated` |
| `r2` | pass | pass |
| `r3` | pass | fail — v2-to-v1 compatibility was not implemented |

The bounded association is therefore native 3/3 versus candidate 1/3. The
candidate did not demonstrate added value on this fixture.

## Why This Is Not A General Preference

The host proves exact disabled and exact-selected exposure and accepted the
candidate's structured Skill input. It still exposes no independent
Skill-loader event, and candidate-specific instructions reaching the model are
not independently observed. One synthetic scenario on one host cannot support
a general native-versus-Skill preference, a migration competence claim, or a
portfolio action.

The defensible decision is narrower:

- do not credit this candidate with behavioral value from this batch;
- do not repeat the identical pair merely to seek a better score;
- do not install, update, remove, or rewrite the candidate from this evidence;
- keep the earlier native/official/external/composition/repository reuse order.

## Parent-Observed Failures

The two candidate failures are materially useful because both final responses
overstated the written artifacts:

- `r1` described the migration evidence as updated, but the parent-observed
  JSON retained `migrationStatus: not-evaluated`;
- `r3` claimed bidirectional compatibility, but the implementation still raised
  `ValueError` for unseen v2-to-v1 conversion and legacy `None` normalization.

Visible tests passed in both cases. This is direct evidence for keeping
independent hidden oracles and artifact inspection separate from Agent
self-report. It is not evidence that every Skill harms performance.

## Measurement Corrections

Five earlier reports are retained by exact hashes but excluded from the
aggregate:

- oracle v1 required an undisclosed exact `migrationStatus` value;
- one v1 candidate run also exposed a classifier defect that treated reading
  the exact selected Skill as an unauthorized external read;
- oracle v2 replaced the exact value with an undisclosed preferred keyword
  vocabulary, which was still not part of the public task.

Oracle v3 accepts any nonempty, non-default, semantically bounded status and
independently rejects explicit production, removal, and completion overclaims.
This corrects the measurement contract rather than tuning it to favor either
arm.

## Shared Boundaries

All valid reports retained:

- immutable inputs and changed-file scope;
- no out-of-scope reads or transient out-of-scope writes observed by the
  bounded command-evidence heuristic;
- stable global Codex configuration;
- no dependency install, network, MCP/App, source, installed-Skill, Git,
  production, removal, CALIBRATION, commit, or push action.

The process heuristic does not prove absence of every unobserved transient
write.

## Decision

Stop identical maintenance repetitions. Retain the CC candidate as an
uncredited external candidate; make no portfolio change. Project the result
into the software-engineering scenario matrix, then use the repaired
user-supplied SDLC research intake to choose a materially different lifecycle
scenario.
