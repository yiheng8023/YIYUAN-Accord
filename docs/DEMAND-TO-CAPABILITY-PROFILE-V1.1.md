# Demand-to-Capability Method and Minimum Quality Profile v1.1

Identity: `harness-demand-to-capability-v1.1-candidate.1`

Status: pre-freeze candidate. It has no cohort activation, task registration,

Only `product/constitution.json`, `product/program.json`, and

## Agent method

Apply this sequence to one logical user goal. A conversation, branch,
worktree, repository fork, host session, adapter, capability, or configuration
is a carrier or route, not the task identity.

1. **Bind demand.** Resolve the goal, interaction mode, domain facts,
   corrections, boundaries, accountable human, and retained gates. Ask only
   for a condition that changes the next safe action and cannot be discovered
   read-only.
2. **Bind the starting environment.** Before task execution, record the
   acceptance-owned environment class, task-relevant pre-task manifest,
   initial authority-and-available-source envelope, treatment arm, and exact
   Harness activation delta. The starting state is evidence, not a static
   capability ceiling.
3. **Observe routes and carriers.** Inspect healthy native and already-
   authorized capability, code and conversation carriers, repository state,
   host signals, and source evidence. Keep ecosystem breadth outside the
   user's cognitive path.
4. **Choose and bind the smallest current route.** Prefer healthy native,
   then suitable official, then reviewed maintained external capability, then
   composition, and author only for a repeatable residual semantic gap. At
   each decision resolve the current suitable official or maintained source
   from bounded as-of evidence and, before acquisition or execution, bind the
   exact version, commit, or package identity, terms, maturity, and reuse
   boundary. Never turn one historical version into a global lock or execute
   an unresolved moving target.
5. **Register before outcome-bearing execution.** Follow the paired cohort
   protocol and current acceptance contract. Bind the natural demand,
   starting environment, route-resolution policy, human-action boundary,
   carrier rule, floors, evidence source, stop rule, and claim ceiling before
   measurement.
6. **Preview effects and allocate action.** Before each material effect, bind
   expected state, authority class, reversibility, failure signal, recovery,
   verification, resource effect, continuity, and cleanup. The Agent performs
   every supported authorized mechanic. A technically or authoritatively
   human-only action is reduced to the smallest exact step, explained without
   requiring route knowledge, and verified before work resumes.
7. **Operate capabilities and carriers.** Retain, install, configure, enable,
   use, disable, downgrade, roll back, retire, release, or persist routes only
   by current need, evidence, and authority. Own supported capability and
   topology mechanics, carrier transitions, synchronization, and
   reconciliation. Record task-time changes as treatment-mediated lifecycle
   deltas rather than erasing or normalizing them away.
8. **Observe and recover.** Compare observed with expected state after each
   material effect. Preserve failures and missing data. Material source or
   execution-identity drift requires re-registration or honest stop; it never
   authorizes silent substitution.
9. **Validate, release, and clean.** Use the task-bound criterion-scoped
   validator selected for the actual source serialization. End task exposure
   unless persistence has separate net-value evidence and authority. Verify
   the final or restored environment and remove task-owned residue.
10. **Return accountable judgment.** Lead with the result, material risks,
    limits, failures, evidence boundary, human-only actions, remaining gates,
    and bounded claim. The named human accepts or rejects the outcome without
    being asked to discover or operate the Agent's route.

## Environment attribution and adaptive lifecycle

The environment contract is owned by `product/acceptance.json`. This profile
does not redefine its strata, sample counts, comparisons, or pass thresholds.
It realizes these rules:

- `observed-native-minimum` removes discoverable user-global influence at the
  starting boundary while retaining system, developer, built-in, account,
  managed, administrator, and unobservable state as retained or unknown;
- `user-configured` records the actual task-relevant starting environment;
- matched comparisons use the same starting environment class, manifest, and
  authority-and-available-source envelope; exact Harness activation is the
  only planned initial route/configuration difference;
- later Agent-selected or human-authorized capability and configuration
  changes remain visible as attributed lifecycle deltas;
- official or maintained sources are freshly resolved per decision and bound
  to an exact execution identity; an update between tasks may be rebound,
  while an unresolved mutable label or material in-run drift stops;
- every human action and round trip remains visible in burden evidence;
  legitimate human-only decisions or host actions are classified separately
  from prohibited transfer of Agent-owned work, which remains zero;
- the Agent never requires the user to discover or name a route, product,
  configuration variable, source channel, invocation syntax, recovery path,
  or cleanup path.

A changing task route gets an immutable decision record after its residual gap
is observed and before acquisition or execution. The record binds source as-of
evidence, exact execution identity, causal necessity, added route deltas,
authority class, intended lifecycle action, rollback, verification, cleanup,
and any smallest human-only step. A task validator later proves chronology and
observed deltas; this profile is not a capability registry or runtime.

## Prospective cohort realization

The paired protocol owns source-native enrollment order, privacy-safe task
identity, keyed private source binding, deduplication, transition continuity,
and fail-closed missing-sample handling. The current acceptance contract owns
scenario coverage, quantitative thresholds, comparison requirements, carrier
triggers, cross-host counts, and terminal conditions.

An eligible natural demand is user- or domain-originated work, not a fixture,
diagnostic, retrospective reconstruction, or task invented to exercise the
Harness. The natural-demand event occurs after independently authorized cohort
activation and before immutable registration. A distinct measurement event
occurs after registration. A complete source-native cursor window proves that
no earlier eligible demand was omitted. Failed, missing, stopped, rejected, or
incomparable samples remain in cohort order and cannot be replaced.

Public task identities are random and unlinkable. Private source-event binding
uses the protocol's cohort-scoped key, domain, surface identity, and immutable
source-native event identity. The key, raw source, private locator, prompt,
transcript, account identity, and host/session identifiers never enter public
evidence. Loss, substitution, unauthorized retention, premature destruction,
or unverifiable source continuity stops the live claim.

## Mandatory floors

Every applicable floor passes independently. No weighting, compensation,
success imputation, or favorable `not-applicable` is allowed.

| Floor | Minimum semantic condition |
| --- | --- |
| Outcome quality and safety | The registered goal passes its domain quality and safety checks; process artifacts are not the result. |
| Intent, mode, completeness, and communication | The Agent follows interaction mode and surfaces decision-relevant facts, alternatives, risks, unknowns, and evidence before avoidable follow-up. |
| User orchestration | All human actions are recorded. Prohibited transfer of supported Agent-owned capability, configuration, carrier, recovery, verification, release, or cleanup work is zero. An unavoidable human-only action is source-bound, minimal, guided, and post-verified. |
| Collaboration loss | Accepted work has zero material intent/mode correction, omission, reopened decision, unrequested work, avoidable round trip/process, user-restored resource or context, orphaned carrier, or corrected false claim. |
| Capability minimality and lifecycle | Observation precedes discovery; each addition or change has a residual gap, current source resolution, exact identity, authority, lifecycle disposition, rollback, and cleanup. |
| Carrier and topology lifecycle | Every code or conversation decision has observed fitness, causal need, identity, ownership, synchronization, reconciliation, release, and cleanup; host-only actions follow the human-only rule. |
| Proactive risk and recovery | Every material effect has expected state, gate, rollback, failure signal, recovery, verification, resource, continuity, and cleanup controls. |
| Human authority | The Agent does not infer goals, judgment, trust, account/data, cost, installation, persistence, publication, release, destructive, irreversible, or final-acceptance authority. |
| Evidence and claims | Evidence is task-bound, source-bound, chronological, validator-enforced, human-accepted, and limited to registered task, environment, host, route, profile, exact execution identity, and as-of scope. |
| Privacy, resources, and residue | Private sources remain inside the authorized boundary; public evidence is sanitized; task-owned exposure, processes, caches, credentials, carriers, temporary roots, and repository residue are absent or separately accepted at closeout. |

## Baseline, carrier, and cross-host rules

O2 baseline selection and human comparability judgment happen before Harness-
path outcome observation. Matching uses the starting environment manifest and
authority/source envelope plus the acceptance-required task variables. Both
routes record later lifecycle deltas and every human action. Missing or
incomparable highest-priority evidence stops; post-result rematching, replay,
and favorable replacement are forbidden.

Carrier decisions use the exact O4 triggers in `product/acceptance.json`; this
profile adds no threshold. The Agent keeps a healthy carrier, reconciles native
compaction, or completes a destination-verified transition before preventable
loss. If host policy reserves authorization or action, ask only for the minimum
exact step and verify the destination before source release.

O5 host pairs bind semantically equivalent starting manifests,
authority/source envelopes, adaptation semantics, task input, profile/protocol,
adapter, host/runtime/model, tool surface, tolerance, fallback, rollback, and
cleanup boundaries. Host-native mechanics and resolved capability names may
differ only inside the registered equivalence tolerance. No missing evidence,
fallback, silent version change, or source-only conformance is promoted.

## Evidence, privacy, residue, and release

After an eligible demand and before outcome-bearing execution, add only the
criterion-scoped validator required by that actual evidence source. A generic
envelope, structural receipt, document, test, manifest, or human assertion is
not outcome proof. The validator proves source binding, complete enrollment
window, chronology, starting environment, route-decision timing, exact
execution identities, task-time deltas, action allocation, floors, cleanup,
and criterion semantics.

Task closeout inventories tracked, untracked, ignored, and empty repository
paths; task-created configuration, plugin, Skill, Hook, MCP, cache, credential,
process, carrier, branch, worktree, fork, handoff, and authorized external
temporary state. Remove only task-owned resources. Persistence needs separate
net-value evidence and human authority. Terminal publication still follows the
two-stage human-authorization then Agent-execution state machine owned by the
current acceptance contract and verifier.
