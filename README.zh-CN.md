# Agent Autonomy Harness

[English](README.md) | 简体中文

> 你只需说明想要的结果；该用什么、怎么推进，由 Agent 负责。

Agent Autonomy Harness 研究的是一种更省心的人机协作：用户提供目标、必要事实、边界
授权、修正和最终判断；Agent 负责理解意图、补足遗漏，选择最小充分路线，并完成执行、
恢复、验证和清理。

任务怎么组织也不该成为用户的功课。默认继续当前对话和代码现场；确有隔离、并行或
权限需要时，Agent 才分支或分叉，并负责同步、回并、归档与收尾。用户不必先学会
Codex、工具或 Git 才能提出需求。

Harness 不是 Agent 运行时、控制平面、Git 或任务管理器。它要交付的是一套开放且不绑定
单一 Agent 的“需求到能力”方法、最低质量要求和薄参考适配器，用来检验这类协作是否
真的减少用户负担。

项目仍处于研究验证阶段；v0.2 当前有一个已预注册的连续性对账交付处于 active。仓库目前有机器可读的
产品契约、确定性验证器和未启用的参考适配器候选；O1 已由公开入口改写以及未安装的 Codex、
Claude 任务级 Skill 源码包三个任务绑定、经用户认可的结果支持。O3 另经任务专属验证，
确认这三项路线决策同时覆盖“不需要新增能力时保留原生路线”和“确有缺口时做有限、来源
固定的官方发现或适配”。O2、O4、O5 仍未通过（当前为 `2/5`）；Claude 与 Codex 的 Skill
源码交付过于相似，不会硬算成 O2 的第三种场景。当前候选把 active 状态下超过 Codex
Hook 4096 字符上限的 6301 字符连续性投影，改为有界、只读的权威、活动工作和 Git 对账
检查点；在任务证据、O2 cohort 验证器和具名人类判断全部通过前，它仍未被接受，也不会
提前改变 O2。

一次临时 Codex 连续性任务真实送达了 Skill，以及启动和压缩后的两次投影，但因预注册
要求的原生 Hook 生命周期记录不可用而停止。后来一次固定源码审查在执行 Claude 前再次
诚实停止：隔离 `CODEX_HOME` 并不会隔离用户全局 Skill，一个与任务不匹配的 code-review
Skill 选择了未登记的并行路线，唯一一次 Codex 调用最终超时且没有最终结果。后续收官
关键路径任务已成功排除 24 个非 Harness Skill 并关闭 multi-agent，但其不可变结构化输出
Schema 中一个常量属性没有写宿主要求的显式类型，调用在模型生成前即被拒绝，Claude
因而没有执行。随后一次上下文载体决策已通过修正后的 Schema、Skill 与拓扑预检，但唯一
一次 Codex 调用又使用内建 `list_mcp_resources`，枚举了 46 个环境中的 App 插件与 Skill
描述。该能力和数据面未被注册，因而触发固定停止，进程被终止，条件式 Claude 调用没有
执行。所有任务的插件、信任、缓存、认证链接、进程和临时文件均已清理，所有 stopped
结果都不增加 O1-O5 进度。

当前 Codex 已提供任务级原生接口，用于检查模型可见提示、精确禁用某个 Skill，以及关闭
multi-agent 工具。今后有测量意义的调度必须由 Agent 先观察可见能力，只在当前任务内拒绝
因果上不适用的路线；若无法证明预期 Skill、数据和拓扑边界，就在模型调用前失败关闭。
用户不需要学习或操作这些配置，Harness 插件也不会覆盖用户更广的能力库存。父 Agent
还必须在消耗唯一模型调用前绑定精确宿主可接受的输出 Schema；一般 JSON Schema 合法
不等于宿主兼容。只排除提示中可见的 Skill 也不等于工具和数据边界完整：在找到官方、
稳定、单次调用级的最小工具面配置，能够约束环境 MCP/App 资源并只保留必要的只读仓库
操作前，当前 Codex 测量路线不具备资格。随后一次无认证、无插件、无模型的 Codex 0.147.0
`app-server` 探针确认，单进程 `apps._default.enabled=false` 会真实生效：已安装或可调用 App
为零，MCP server 为零。但同一个隔离 home 仍发现 39 个启用 Skill，其中 33 个来自可替换的
CC Switch 共享目录，六个来自 Codex 系统目录；所以隔离 home 不等于隔离能力，CC Switch
也不是 Harness 依赖。该探针尚不能证明未来线程的模型可见工具规格，也不能证明与模型驱动
仓库操作共存；下一次注册必须在调用前核对这些精确表面，并约束未授权资源、调用和效果，
而不是在没有因果必要性时强求宿主连无害的内建入口都不存在。这是父 Agent 的调度约束，
不授权新增通用能力管理器或控制平面。准确状态以仓库验证器为准。

## 目标交互

假设用户只说：

> 审计这个仓库，把它整理到可以公开发布的状态。未经我确认，不要真的发布。

理想状态下，Agent 应该：

1. 理解目标，以及“不得自行发布”的边界；
2. 先判断健康且已授权的原生能力是否足够；
3. 只有存在真实缺口时，才发现或增加外部能力；
4. 默认继续当前任务和 checkout；只有隔离、并行、宿主容量或权威边界确有必要时，才
   创建分支、worktree、仓库 fork、对话分叉或新任务；
5. 主动判断当前对话是否仍是安全载体，在可避免的上下文损失发生前完成原生压缩或
   经验证的交接，不让用户猜什么时候该换任务；
6. 任何这类载体的同步、代码合并或结论回并、归档或释放、清理由 Agent 负责；
7. 只向用户询问缺失事实、关键判断或新增授权，而不是让用户指定工具和调用方法；
8. 完成执行、故障恢复和结果验证，结束任务级能力暴露，并清理任务产生的残留；
9. 把结果与证据交给用户作最终判断。

这是产品要验证的目标交互，不代表当前已经具备这些运行能力。

## Harness 负责什么

| Harness 自己负责 | Harness 优先复用 | Harness 不会变成 |
| --- | --- | --- |
| “需求到能力”的人机协作方法论 | Agent 健康可用的原生能力 | 通用 Agent 运行时 |
| 开放的最低质量一致性剖面 | 适用时采用 MCP、A2A、CHAP 等工具或协作协议 | 固定能力目录或能力市场 |
| 用户负担、结果质量、权威、证据、恢复、上下文载体健康与转场、代码与对话任务拓扑生命周期、资源生命周期和清理的评价要求 | 已有的发现、身份、授权、审计、溯源、评价、Git 和宿主任务原语 | 在没有剩余缺口时另造线协议、上下文监控器、Git 或任务管理器、身份系统或审计格式 |
| 在真实宿主上检验共同语义的薄参考适配器 | 已记录来源、版本、许可或适用条款、成熟度和边界的外部实现 | 人类目标、专业判断、同意权与最终责任的替代者 |

Codex 是第一个参考宿主，因为它适合作为高水平、可落地的试验样本。Codex 专属配置不
属于可移植核心；在不同的第二 Agent 宿主或运行时上完成证明前，不得宣称跨宿主成立。

## 仓库目前有什么

当前仓库提供：

- 描述目的和固定边界的机器可读[产品宪法](product/constitution.json)；
- 描述当前因果工作状态的[产品工序](product/program.json)；
- 明确的 [v0.2 验收标准](product/acceptance.json)；
- 一个供未来 Codex cohort 任务精确预注册的[未验收候选方法与最低质量 profile](docs/DEMAND-TO-CAPABILITY-PROFILE.md)；
- 只依赖 Python 标准库的验证器，用于拒绝无效权威、证据、工作图和仓库残留；
- 一个只依赖 Python 标准库、尚未启用的 Codex `SessionStart` 适配器候选；它在启动、
  恢复、清空或压缩后投影当前权威，不读取提示词或 transcript 内容，也不保存会话状态；
- 一个尚未启用的 Codex 薄插件源码候选；其中一个任务级 Skill 投影未验收的方法，一个
  Hook 封装接续适配器；工作区发现入口只将它标记为 `AVAILABLE`，不会安装、启用或信任它；
- 一份内容寻址的 Codex 连续性停止结果：精确临时安装确实送达了 Skill 及启动/压缩两次
  投影，但缺失的原生 Hook 事件证据仍按强制底线判为失败，随后完整恢复消费者状态；
- 一个尚未启用的 Claude Code Skill+Hook 薄投影；它复用同一候选方法，把宿主原生
  `SessionStart` 输入和 stdout 上下文输出翻译为相同的仓库接续语义，并且可只在单个
  会话内暴露而无需持久安装；
- 针对公开验证入口的产品测试；
- 固定来源的外部方案审查，用来缩小自研边界，避免重复造轮子。

仓库目前不提供任务执行、持久能力安装、已经验收的实时路由或质量剖面。适配器没有
安装进用户配置。仓库验证通过和这次停止的实时机制结果，都不能证明产品已经形成经
验收的用户价值。

## 验证仓库

前置条件是 Git 与 Python 3.10 或更高版本；无需安装 Python 包、连接账号或调用外部
服务。

```powershell
git clone https://github.com/yiheng8023/agent-autonomy-harness.git
cd agent-autonomy-harness
python -B -m harness verify --root . --json
python -B -m unittest discover -s tests/product -v
```

JSON 报告是当前机器状态面；工作边界见[接续说明](docs/operations/CONTINUATION.md)。

## v0.2 必须证明什么

- **O1——一次完整闭环：**一个自然的目标级任务完成时，用户不需要替 Agent 选择、
  调用、恢复、验证或清理能力路线，也不需要选择、操作、回并、归档或清理代码与对话
  拓扑；同时不得发生需要用户纠正的重大协作损失，例如意图误解、重开已定决策、未
  请求工作、过程膨胀、残留、接续失败、拓扑分叉失控或虚假收官声明。
- **O2——重复降低负担：**至少三个实质不同的自然任务，相比来源明确的临时协作基线
  重复满足这一零损失底线并减少用户编排负担，而且任务质量不能下降。
- **O3——按需能力生命周期：**同时包含“不需要新增能力”和“确有缺口才发现能力”两类
  情况；路线决策有证据、有边界，任务级能力暴露在结束后释放。
- **O4——校准方法论与质量剖面：**在 Codex 参考宿主上，用同一套预先固定的标准评价
  通过和失败的真实任务记录；这一项本身不能宣称 Agent 中立或跨宿主成立。
- **O5——有限跨宿主证明：**同一个任务与核心语义，通过薄适配器在 Codex 和不同的第二
  Agent 宿主或运行时上得到可接受且等价的结果。

在 O1-O4 中，自然任务是预注册的逻辑需求与结果单元，不是 Codex 侧边栏中的任务或
线程。多个顺序 receipt 可以留在一个健康的宿主任务中；同一 receipt 只有分别满足各
criterion 的预注册与验证负担时，才能同时支持多个 criterion，且不能在同一 criterion
内重复凑足样本数。

已经授权的产品计划交付，本身就是实际需求，前提是它的主要目的确实是产出所需交付物，
而不是为了演练或诊断 Harness。这个区分不会免除预注册、证据、强制底线和具名人类验收。

人类权威、零信任证据、精简独立权威和有限过程/资源损失是强制护栏，但不能代替
产品结果。

## 设计原则

- 从用户目标出发，而不是从工具名或能力目录出发。
- 默认留在当前健康任务和 checkout；只有确有因果必要才分叉，由 Agent 负责同步、
  回并、归档、释放和清理。
- 先观察健康且已授权的现有能力，再决定是否继续寻找。
- 只有证据表明确有剩余缺口时才增加能力；任务结束后释放任务级暴露。
- 先复用已有充分协议、运行时与证据层，确有集成或语义缺口才组合或自研。
- 目标、重大判断、新信任、费用、公开发布和不可逆操作始终由人掌握。
- 任何声明都不能超过来源明确的证据所能证明的范围。
