# Complete self-bootstrapping feasibility and reuse study

Status: feasibility stage completed, 2026-08-28. This is an admitted design input, not
runtime authority, implementation approval, behavior evidence or release
evidence.

## Decision

Complete self-bootstrapping is **conditionally feasible for bounded outcome
classes**, not as universal autonomous self-improvement. The feasible product
core is a small semantic and evaluation contract that can:

1. observe the exposed environment and mark the rest unknown;
2. bind the current outcome, accountable consensus and human-owned authority;
3. discover and compare native, maintained, composable and authored routes;
4. establish only the minimum reversible means;
5. verify declaration, activation, execution, consequence and post-state as
   separate facts;
6. retain learning only through an observed state carrier and a full acceptance
   vector; and
7. roll back, release or retire the means when fitness falls or lifecycle cost
   exceeds value.

The current decision has advanced from the P0-P3 **conditional-go for semantic
modelling** through completed P4 and one minimum pure-data reference core.
It remains **no-go for a live mechanism, a new runtime, a general state store or
release work**. Exact checkpoint `553f5a97e08390117e877e7b913c7a501018bfa5`
retains failed GT-14 through GT-16 attempts because their publishable source is
not task-complete; source-complete replay remains active. GT-17 global-consensus
reconciliation and GT-18 longitudinal evolution remain unperformed.

The unbounded interpretation is infeasible: no system can guarantee complete
visibility into every host, infer human values or authority from context,
prove its own real-world value, find a globally optimal route across unknown
future capabilities, or undo arbitrary irreversible external effects. Accord
must therefore make `unknown`, claim narrowing and honest stop part of the
successful loop.

## Scope and method

This study decomposes self-bootstrapping rather than treating it as one binary
feature. It compares no-build, native reuse, protocol composition, maintained
framework reuse and bounded authorship. Primary sources are favored, but a
source's official status or author's reputation is evidence about provenance,
not evidence of fit. No third-party code or dependency has been added.

### GT-15 source-bound decision chain

The named sub-capability for this replay is **discover and select the minimum
replaceable route before authorship**. Its claim is feasibility and route
fitness only. It does not claim that an external wheel is installed, activated,
effective or required, or that the complete self-bootstrapping loop works.

The comparison is bound as follows:

1. **Outcome and baseline:** decide whether the pure-data core at repository
   revision `e080b303ea078eecfe147140646a73d249d5beb1`, with `closure.py`
   SHA-256 `f1081db8c89d7ab4a18daf3a3640abc83db51eb46765f9220eba3193aa1c9570`,
   can stay dependency-free while host discovery, composition and continuity
   remain replaceable responsibilities. The route baseline is this
   current-enabled host's already exposed read-only capability with no new
   task mechanism; it is not a native, official-clean or no-Accord environment
   baseline.
2. **Counterfactual:** compare no-build, one suitable maintained reuse route,
   a bounded composition and bounded authorship under the same responsibility
   and authority envelope. Environment arms and route alternatives remain
   different concepts.
3. **Falsifiable hypothesis:** an existing route is reusable only if current
   primary-source provenance, license, maintenance and package facts are known,
   it closes the named responsibility without new ungranted authority, and its
   effect, isolation, recovery and retirement burden is not dominated by a
   smaller route.
4. **Hard gates before preference:** unknown license for the copied component,
   unavailable independent consequence evidence, hidden trust/data expansion,
   missing rollback or retirement, or a materially mismatched runtime fails
   adoption. Popularity, author reputation and a local proxy gain cannot
   compensate.
5. **Decision:** retain no-build for the core; admit protocol or framework
   patterns as replaceable adapter candidates only. Install or copy nothing
   until a later representative gap proves that the current host-native route
   cannot close the obligation and a bounded probe passes the same full vector.
6. **Invalidation:** repository revision, package release, license, maintenance,
   host surface, authority, evaluator, claim or observed responsibility change
   invalidates only the affected comparison and replays from its source fact.

This ordering prevents a green implementation probe from retroactively proving
that its source, baseline, authority or product-form premise was valid.

### Bounded high-risk route probe

A task-owned pure-data request with SHA-256
`af8e872b054d21cba2d025d600dffdd87aeedd77c641b5d3056331522bbe0b81`
replayed the exact obligation through `reconcile_closure`. It compared the
observed native read-only research route with an `autoresearch` pattern copy,
OpenAI Agents SDK, an MCP composition, LangGraph, Temporal and bounded
authorship. The independent deterministic oracle observed:

- `valid=true`, `disposition=no-op`, selected route
  `native-read-only-no-add`, and completion allowed;
- bounded authorship passed hard gates but was Pareto-dominated by no-build;
- every copied, framework or composition route failed at least one current
  responsibility, license, fit, independent-evidence, authority or coherence
  gate; and
- no package was downloaded, installed, imported or executed, and the exact
  task-owned fixture directory was removed and independently observed absent.

This probe verifies the route selector and the current no-build decision only.
Its historical fixture label `native-read-only-no-add` means host-native
read-only capability in the current-enabled composition, not an official-clean
or no-Accord arm.
It is not installation, activation, live-adapter behavior, field value or a
passing GT-15 observation. GT-15 still requires a publishable source record and
observation binding that preserve this ledger and post-capture cleanup without
retroactively rewriting the retained failed attempt.

The concern that plugins and Skills alone may not provide systematic,
persistent, flexible end-to-end closure is admitted as an architecture pressure,
not as a proved universal deficiency. Each projection must be tested against
named responsibilities such as activation, continuity, state lifecycle,
independent observation and retirement. The answer may be one sufficient form,
several replaceable forms under shared contracts, or no Accord-owned artifact;
it is not a preselected Runtime or a fixed catalogue.

The current Codex and Claude Code hosts are Accord-enabled and contain other
extensions. Their listings are environment observations, not clean baselines.
No credential-bearing configuration, session content or unrelated persistent
state was inspected. The historical GT-07, GT-11, GT-12 and GT-13 observations
remain regression and counterevidence inputs; they do not satisfy this study's
prototype gates.

## Adoption ledger

### Karpathy: small legible reference implementations

Sources: [micrograd](https://github.com/karpathy/micrograd),
[microgpt](https://karpathy.github.io/2026/02/12/microgpt/),
[nanoGPT](https://github.com/karpathy/nanoGPT), and
[llm.c](https://github.com/karpathy/llm.c). The bound `micrograd`, `nanoGPT`
and `llm.c` repository metadata reports MIT; `microgpt` is an article, not a
reusable package.

- **Admit as a design pattern:** expose the irreducible end-to-end algorithm in
  a small readable reference implementation; keep optimized or host-specific
  paths replaceable; cross-check them against a simpler reference.
- **Why it fits:** Accord needs a reviewable semantic core whose complete loop
  can be understood without loading every adapter, evaluator or historical
  mechanism.
- **Do not inherit:** neural-network domain assumptions, line count as a goal,
  educational completeness as production fitness, or an author's aesthetic as
  authority.
- **Counterevidence:** `micrograd` describes itself as potentially educational;
  the current `nanoGPT` README marks that repository old and deprecated in
  favor of `nanochat`; `llm.c` demonstrates that a small reference and an
  optimized implementation can have different portability and dependency
  envelopes.
- **Exit condition:** reject the pattern if the “small core” hides authority,
  effects, failure recovery or lifecycle work in undocumented adapters.

### Karpathy: autoresearch bounded experiment operator

Source: [autoresearch](https://github.com/karpathy/autoresearch). Its bound
README declares MIT, but the exact tree lacks a standalone `LICENSE`; this
review therefore admits the pattern and does not copy code.

- **Admit as a prototype pattern only:** one explicitly mutable file, a fixed
  evaluator outside that surface, a fixed five-minute budget, a logged
  keep/discard/crash decision and reviewable diffs.
- **Why it fits:** this is a concrete operator for one part of self-evolution.
  It makes mutation scope, budget and retention explicit.
- **Do not inherit:** its single `val_bpb` objective, single-GPU assumption,
  overnight autonomy, domain-specific training harness or platform-specific
  comparability. Its README says results are not comparable across different
  compute platforms.
- **Missing Accord controls:** current outcome and human authority binding,
  multi-dimensional acceptance, environment contamination, consequence-level
  verification, external side effects, continuity migration and retirement.
- **Exit condition:** discard any experiment operator that can edit its own
  evaluator, optimize one proxy while regressing another acceptance dimension,
  retain a change without independent post-state evidence, or expand authority.

Self-evolution is therefore admitted only as:

```text
bounded hypothesis
-> isolated mutation
-> immutable multi-dimensional evaluation
-> independent effect and residue check
-> keep | discard | rollback | stop
```

It is not the self-bootstrapping core.

Sources: [MCP architecture](https://modelcontextprotocol.io/specification/2025-06-18/architecture)

The project is transitioning contributions from MIT to Apache-2.0; documentation

- **Do not infer:** listed means authorized, healthy, model-effective, safe or

### LangGraph and Temporal

Sources: [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence),
[LangGraph human-in-the-loop](https://docs.langchain.com/oss/python/langchain/human-in-the-loop)
and [Temporal Workflow Execution](https://docs.temporal.io/workflow-execution).
The reviewed LangGraph and Temporal repositories use the MIT license.

- **Potential reuse:** LangGraph checkpoints support pause/resume, inspection,
  fault recovery and time-travel-style replay; Temporal provides durable event
  history and deterministic replay for long-running workflows.
- **Limits:** both introduce a runtime and state lifecycle. Serialization,
  deterministic replay, storage, privacy, upgrades, deletion and operations are
  real costs. A workflow checkpoint is not an accountable product consensus,
  and replay is not proof that the real-world effect is correct.
- **Decision:** conditional alternatives for the durable-state prototype, not
  the default product form. Prefer an observed host-bound carrier when it closes
  the task with lower lifecycle cost.

### OPA, OpenTelemetry and container isolation

Sources: [OPA integration](https://www.openpolicyagent.org/docs/integration),
[OPA decision logs](https://www.openpolicyagent.org/docs/management-decision-logs),
[OpenTelemetry observability primer](https://opentelemetry.io/docs/concepts/observability-primer/)
and [Docker resource constraints](https://docs.docker.com/engine/containers/resource_constraints/).
OPA, OpenTelemetry specifications and Moby use Apache-2.0.

- **Potential reuse:** OPA-style pure policy decisions and decision IDs;
  OpenTelemetry-style trace/span correlation and instrumentation scope; bounded
  containers for disposable comparisons and resource limits.
- **Limits:** policy evaluates supplied facts but does not create human
  authority; decision logs and traces can expose sensitive inputs; telemetry is
  not effect or value; containers have platform/kernel differences and do not
  automatically produce an official-clean host or remove network/account
  contamination. Docker documents that containers have no resource constraints
  by default.
- **Decision:** adopt the semantic patterns selectively. Do not add an OPA
  service, telemetry backend or container requirement before a prototype proves
  its necessity and cleanup path.

## Prior Accord counterevidence that constrains the design

The project history already falsifies several tempting shortcuts:

- adding rules, states, validators and fallback layers can recreate the
  complexity Accord is meant to remove;
- installation or declaration does not prove effective capability;
- local success, a commit, push or hosted check is not outcome completion;
- historical success can be stale in a changed host;
- a strong Agent may repair locally by adding mechanisms instead of revisiting
  a false premise;
- evidence ceremony can itself increase interference and cleanup risk;
- a fallback does not need to become a complete second runtime: rollback,
  degradation, claim narrowing and honest stop are valid outcomes; and
- history should remain in Git and bounded evidence, not on every runtime path.

These are not arguments against self-bootstrapping. They define its minimum
safety and subtraction properties.

| Risk | Required control | Failure disposition |
| --- | --- | --- |

| Single proxy becomes the goal | Immutable full acceptance vector with burden, interference, authority, effect and lifecycle | Discard or roll back |
| Evaluator or baseline drifts with mutation | Separate immutable evaluator and versioned baseline | Invalidate comparison |

## Bounded prototype program

No prototype may install into or reconfigure the live Codex or Claude Code host.
No prototype may read credentials, session contents or unrelated persistent
state. Use disposable fixtures and task-owned paths only.

1. **P0 — environment admission:** derive a minimal provenance snapshot from a
   synthetic host inventory; distinguish declared, enabled, activated,
   executed and effect-observed states; prove unknown and cleanup behavior.
2. **P1 — reuse-before-build:** change one synthetic capability listing and
   compare no-op, native reuse, composition and bounded authorship. The selected
   route must change only when the outcome relation or constraint changes.
3. **P2 — bounded evolution:** permit one task-owned artifact to mutate under an
   immutable evaluator and fixed budget. A single improved proxy with a worse
   authority, burden, interference, effect or lifecycle dimension must be
   discarded or rolled back.
4. **P3 — continuity carrier:** compare no durable state, a bound host carrier
   and one replaceable durable carrier through correction, interruption,
   resumption, migration and retirement. Static instructions must fail the
   current-state test.
5. **P4 — complete vertical slice:** combine P0–P3 for one representative task
   and independently verify consequence and zero task residue. This is the
   earliest evidence that can authorize reference-core implementation.

## P0 prototype result: environment admission

Disposition: **logic-feasible for the bounded question; not product behavior
evidence**.

On 2026-08-28 a task-owned, in-memory, single-file HTML logic prototype drove
four environment-admission scenarios in local headless Chrome. It did not read
or alter the live Codex or Claude Code configuration, plugins, credentials,
session content or unrelated state. The prototype and rendered screenshots were
discarded after the result was captured here because the bound checkout forbids
the throwaway Git branch normally used for prototype custody.

The prototype falsified a tempting linear state machine. Declaration,
enablement, activation, execution and effect must be independent tri-state
observations (`observed`, `not-observed`, `unknown`) connected by explicit
causal relations. An effect may be independently observed before an activation
or execution event becomes visible; the effect remains a fact while the causal
gap remains visible. No later observation backfills an earlier one.

Four scenarios produced the intended bounded decisions:

1. declared and enabled Accord in a current composed environment with material
   confounding and available isolation selected `isolate`, without claiming
   activation, execution or effect;
2. an independently observed effect in the current composed environment with
   activation and execution unknown admitted only the composed arm and exposed
   the `execution -> effect` causal gap;
3. unknown provenance with no available isolation selected `narrow-claim`
   rather than inventing a baseline or permanently blocking unrelated work; and
4. an isolated environment with directly observed no-Accord exposure, no known
   material confounding and verified cleanup selected `admit-scoped-baseline`.

The derived design rule is:

```text
independent evidence facts
+ explicit causal gaps
+ scoped provenance and Accord exposure
+ claim risk and isolation availability
-> admit composed arm | isolate | narrow claim | admit scoped baseline | stop
```

“Clean” is therefore not a permanent host label. It is a scoped admission claim
whose provenance, exposure, confounders and cleanup must all be bound to the
observation. P0 supported continuing feasibility research; the later P1-P3
results complete that bounded study while the implementation gate remains closed.

## P1 prototype result: reuse before authorship

Disposition: **logic-feasible for the bounded question; not a capability,
integration or value claim**.

On 2026-08-28 a second task-owned, in-memory HTML prototype drove five synthetic
route-selection scenarios in local headless Chrome. It did not query a live
registry, install a capability or alter either host. Its candidate records were
fixtures, not assertions about native or third-party capability. The prototype
and screenshots were discarded after this result was captured.

The prototype rejected a universal weighted score for “lowest total burden.” A
single score hides incomparable tradeoffs and makes its weights a second source
of product authority. The viable selector has four ordered layers:

1. establish that a current residual responsibility gap is known; otherwise
   select no-op, inspect or narrow the claim;
2. admit only routes that close the required relations, are currently observed
   available, remain within current authority, have an independent consequence
   verifier and satisfy hard task constraints;
3. remove lifecycle-dominated routes across human burden, interference,
   persistence, recovery and maintenance rather than averaging the dimensions;
4. use native, maintained composition and bounded authorship as a tie-breaker
   only when admitted routes have equivalent fitness, not as a substitute for
   closure or task context.

Five scenarios produced the intended decisions:

1. a complete native whole loop selected `no-op` even when composition and
   authored candidates were also listed;
2. a partial native route, a complete maintained composition and a heavier
   authored runtime selected the composition as the unique non-dominated route;
3. an authored route requiring new authority selected
   `request-minimum-authority` rather than self-authorizing;
4. a listed tool with unknown health and verification selected
   `probe-or-narrow` rather than silently falling back to authorship; and
5. low-latency native and low-interference composition routes remained on the
   Pareto frontier and selected `derive-missing-context-constraint` rather than
   inventing a global ranking.

The derived design rule is:

```text
known residual responsibility gap
-> closure + availability + authority + verifier + hard-constraint admission
-> lifecycle Pareto frontier
-> context-derived constraint
-> equivalent-fitness reuse tie-breaker
-> select | probe | request authority | narrow | honest stop
```

This keeps “reuse before build” strong without turning native or popular
software into authority. It also narrows the intended dynamic relation graph:
candidate discovery is a freshness-bound input, while admission and selection
are derived from the current outcome relations and constraints. P1 supported
continuing feasibility research; P2 and P3 subsequently completed that bounded
study while the implementation gate remains closed.

## P2 prototype result: bounded evolution

Disposition: **logic-feasible as a transaction inside self-bootstrapping; not
evidence of autonomous product improvement or field value**.

On 2026-08-28 a third task-owned, in-memory HTML prototype drove six bounded
evolution scenarios in local headless Chrome. It used an exact baseline, one
task-owned mutable candidate surface, an immutable evaluator, a three-attempt
budget, mandatory rollback and a multi-dimensional acceptance vector. It did
not modify Accord, either host, a model, an evaluator or persistent state.

The prototype showed that `keep` and `discard` are insufficient lifecycle
states. The minimum safe disposition set is:

```text
keep-after-independent-poststate
| discard-and-rollback
| invalidate-and-rollback
| hold-unknown
| revisit-premise-or-retire
```

Six scenarios produced the intended decisions:

1. a higher outcome proxy with worse human burden exceeded the pre-authorized
   zero tolerance and selected `discard-rollback`;
2. an outcome improvement with preserved authority, independent evidence,
   verified cleanup and no regressed dimension selected
   `keep-after-poststate`;
3. a candidate that influenced the evaluator selected `invalid-rollback`, even
   though its reported vector improved;
4. a larger outcome improvement with human burden `+1` was retainable only
   because that exact tolerance was fixed before the candidate was evaluated;
5. an otherwise passing candidate with unknown independent effect or cleanup
   post-state selected `hold-unknown`; and
6. three failed attempts exhausted the fixed budget and selected
   `revisit-premise-or-retire` rather than expanding the loop.

The derived design rule is:

```text
exact baseline + fixed budget + bounded mutable surface + immutable evaluator
-> hard authority and independence gates
-> full acceptance vector against pre-authorized tolerances
-> independent effect and cleanup post-state
-> keep | discard/rollback | invalidate/rollback | hold unknown | retire
```

A one-metric loop is admissible only when the bounded outcome really is
one-dimensional and every other acceptance dimension is an invariant. Accord's
own evolution cannot make that assumption: outcome, human burden, interference,
authority, evidence quality, reversibility and lifecycle cost must remain
visible. P2 supports bounded self-evolution as one operator; it does not make
self-evolution the product core. The implementation gate remains closed.

## P3 prototype result: continuity carrier admission

Disposition: **logic-feasible for carrier admission and retirement; not
evidence that a durable carrier is needed or that cross-host continuity works**.

On 2026-08-28 a fourth task-owned, in-memory HTML prototype drove six
continuity scenarios in local headless Chrome on Windows. It compared no
durable state, a bound host task and an abstract replaceable durable carrier.
It did not read a real conversation, configuration, credential, checkpoint or
database and did not alter either host. The first rendering invocation
malformed its local-file query parameter and produced browser error pages; that
tooling result was rejected, the invocation was corrected and all six intended
scenarios were rendered and visually reviewed.

The prototype established an ordered admission rule rather than a default
state architecture:

1. when the current result has no cross-session obligation, select
   `no-durable-state`;
2. when a bound host carrier is directly observed current, healthy and
   recoverable, including observed resumption after interruption, select
   `use-host-bound-carrier`;
3. admit `admit-replaceable-durable-carrier` only for a real cross-host or
   long-lived obligation with explicit owner, schema, version, TTL, privacy,
   migration, deletion and retirement;
4. static instructions or unknown currentness select `verify-or-narrow`, not
   resumption from assumed state;
5. when newer accountable consensus conflicts with an old derived snapshot,
   select `refresh-derived-state`; and
6. when migration, deletion or retirement is known missing, select
   `reject-durable-carrier` before a more general unknown-health disposition.

The last ordering matters: a known lifecycle failure must not be hidden behind
an unrelated unknown that merely invites more probing. The derived design rule
is:

```text
observed continuity obligation
+ current authority and freshness
+ host-carrier health and recovery evidence
+ durable lifecycle contract only when still necessary
-> no state | host-bound | replaceable durable | refresh | verify/narrow | reject
```

A carrier stores or transports accountable state; it does not become its
authority. Static documentation describes rules, not current progress. Derived
indexes and snapshots must be refreshable from the bound authority and must
support migration, deletion and retirement before they can be admitted. P3
therefore supports carrier pluralism and default subtraction, not a general
state service.

## P4 prototype result: complete product-form-neutral vertical slice

Disposition: **the bounded selection and lifecycle logic is feasible and admits
only a minimum pure-data reference core; no live mechanism, host behavior, user
value or release claim is admitted**.

On 2026-08-28 a task-owned, single-file HTML logic prototype combined P0–P3 for
one synthetic representative obligation: preserve an exact corrected delivery
brief across one bounded carrier interruption, execute the outcome, observe the
consequence independently and release every task-owned continuity resource. It
compared the same responsibility and closure contract across four routes:

1. no added mechanism using only the observed native envelope;
2. the current plugin projection with declaration and enablement observed but
   activation, execution and effect unknown;
3. a replaceable composition of the native executor, a task-scoped handoff
   carrier and an independent effect/post-state probe; and
4. a bounded authored persistent controller.

The prototype ran in headless Chrome with extensions disabled and a separate
task-owned user-data directory for every scenario. Its facts were synthetic and
in-memory. It did not inspect or mutate the installed Accord projection, Codex,
Claude Code, credentials, conversation content, live configuration or unrelated
persistent state. An Oracle module outside the pure reducer could observe the
exported state but could not edit the route, evaluator, tolerance or post-state.
The external driver captured the Oracle result after each complete scenario.

| Scenario | Selected route | Effect/post-state | Decision |
| --- | --- | --- | --- |
| missing native continuity, plugin effect unknown | minimum replaceable composition | observed / zero task residue | bounded loop closed |
| native whole loop independently observed | no added mechanism | observed / zero task residue | bounded loop closed with no Accord-specific mechanism |
| successful effect followed by injected cleanup failure | minimum replaceable composition | observed / residue observed | completion rejected |
| plugin declared and enabled while activation/execution/effect remain unknown | minimum replaceable composition remains the only admitted route | not observed / unknown | installation and enablement did not earn an effect claim |

The selected route was derived in three non-compensating steps: derive the
current admission conditions from this outcome, human authority, compliance,
claim and observed environment, then close every applicable responsibility and
condition without turning the P4 fixture into a universal policy list; remove
lifecycle-dominated routes by Pareto comparison; use no-op, native or maintained
reuse only as a tie-breaker among equivalent-fit routes. The authored persistent controller passed the synthetic closure conditions
but was dominated by the minimum composition on human burden, interference,
persistence, recovery, maintenance and retirement. A bounded proposal to adopt
it was therefore discarded and rolled back even though it could have improved
one proxy such as latency.

This result falsifies both fixed-form extremes. A plugin installation is not a
complete system, while a persistent controller is not justified merely because
one bounded gap exists. The stable product contribution is the small semantic
and decision core: consume provenance-bound observations and responsibility
offers, keep unknowns explicit, apply hard gates, derive the Pareto frontier,
record the exact selection or honest stop, and bind execution, effect,
experiment, rollback, cleanup and retirement states. Environment snapshots,
route instances, task resources and host adapters remain replaceable inputs or
ephemeral evidence rather than a second authority source.

The P4 gate therefore admits the next implementation stage with these limits:

- implement a deterministic, side-effect-free reference module over plain data
  whose compliance invariants are stable but whose outcome conditions,
  thresholds, dimensions and policies are supplied and versioned at task time;
- keep the form catalogue, host discovery, execution, storage and evaluator
  outside the core behind replaceable inputs or interfaces;
- preserve the current semantic model, dynamic graph vocabulary, environment
  admission contract and ten-dimension acceptance vector;
- add no Runtime, service, database, Hook, background process or durable state;
- hard-code no host, tool, product form, workflow, non-compliance policy or
  universal route threshold; and
- fail closed on missing authority, independent evidence, coherence, cleanup or
  an observed continuity carrier; and
- do not promote this synthetic result into GT-14–GT-18 behavior, comparative
  value, cross-host portability, candidate readiness or release evidence.

The HTML prototype, isolated browser profiles, DOM captures and screenshot were
task-owned disposable artifacts. They are removed after this decision is mapped
into the versioned product record because the bound checkout forbids the
throwaway Git branch normally used for prototype custody. The reviewable answer
and its explicit claim ceiling remain here. The admitted reference core is now
implemented. The first GT-14 through GT-16 attempt is retained as failed
counterevidence because fixture summaries and hashes did not preserve all
task-required source facts; the active stage remains
`replay-activation-effect-evidence-and-lifecycle`.

### Weak-link order and current preferred route

1. Preserve the failed GT-14 through GT-16 attempts and their public claim
   exclusions; fix the evidence contract so continuing states cannot omit a
   retained failure.
2. Create source-complete, task-owned GT-14 through GT-16 replays that bind the
   environment, primary sources and full non-compensating consequence/lifecycle
   vector at creation time rather than reconstructing them later.
3. Run GT-17 and GT-18 to test global consensus propagation, a real observed
   carrier, useful later-route change, regression rejection, invalidation and
   rollback or retirement.
4. Re-evaluate the responsibility-to-form graph. Prefer no-op or existing
   healthy routes; admit a Skill, plugin, Hook, protocol, state carrier,
   runtime, service, client, cloud component or composition only for an observed
   unclosed responsibility and keep it replaceable.
5. Refresh this balance ledger, prioritize hard gates and Pareto improvements,
   implement only justified minimum remediations, and replay every affected
   acceptance and lifecycle surface.
6. Reduce user-facing concept load and internal maintenance burden where it does
   not weaken evidence or capability closure; preserve explicit residual risks.
7. Submit one clean exact candidate to independent product, specification,
   implementation and standards review, rechecking zero task residue without
   weakening preservation of foreign, shared or unknown state. Hosted
   verification, named-human release authorization, tag and public Release
   remain later ordered gates.

The current optimal decision is therefore **not** to add a Runtime or another
host projection now. It is to strengthen source capture, isolated consequence
evidence, longitudinal continuity and global reconciliation first. Those facts
can later justify a durable carrier or a multi-form system; absent them, a
larger mechanism would improve architectural appearance while worsening the
very balance this review is meant to protect.
